# Radiance 1.17 MXFP4 Compatibility Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Identify and safely integrate a relevant Radiance 1.17 MXFP4 kernel improvement without replacing the vLLM stack.

**Architecture:** Compare the fork's pinned, patched Python R4D implementation with the Radiance v1.17.0 plugin implementation. Adapt a compatible improvement to the existing Python interface only after establishing its data layout and correctness requirements.

**Tech Stack:** Python, HIP, ROCm, Docker, vLLM, AMD gfx1201.

**Spec:** `docs/superpowers/specs/2026-11-09-radiance-117-design.md`

## Global Constraints

- Retain vLLM and existing model formats, launchers, fallbacks and fork-specific extensions.
- Target one R9700 (gfx1201), TP=1; do not modify multi-GPU paths.
- Pin upstream Radiance to v1.17.0 commit `19d4e8fe0e18071b9b6300f15fc4ccf38dc4fa3d`.
- Do not claim a speedup without GPU measurements; never weaken numerical correctness tests.

## Review Focus

- MXFP4 nibble and E8M0 scale layouts: compare output against an independent dequantization oracle.
- Unusual exponent differences and FP8 subnormals: include boundary values in the oracle test.
- Small and partial M dimensions: check decode and prefill shapes, including nonmultiples of tile size.
- Unavailable R4D or unsupported shapes: preserve the existing fallback or explicit refusal.
- GPU graph replay and repeated execution: compare repeated results to eager execution on hardware.
